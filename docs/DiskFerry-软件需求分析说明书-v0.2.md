## 2. 最终产品目标

### 2.1 一句话定义

**盘渡让 NTFS 磁盘在 Mac 上像普通本地外置卷一样使用：插入即可工作，读写可靠，正常时安静，异常时说清楚。**

### 2.2 五个核心目标

| 目标 | 用户获得的结果 | 判断方式 |
| --- | --- | --- |
| 原生融入 | Finder、打开/保存面板及常用应用能直接使用 NTFS 卷 | 完成完整文件操作流程，无需专用文件浏览器 |
| 可靠读写 | 成功保存并安全弹出的数据可在 Mac、Windows 往返读取 | 内容哈希、目录及元数据验证通过 |
| 默认安静 | 正常插盘、使用、弹出不出现盘渡主窗口或重复通知 | 正常路径新增弹窗和通知均为 0 |
| M 系列优先 | 原生 arm64 运行，围绕现代 macOS 设计安装和扩展机制 | 不依赖 Rosetta，逐项实机验证 |
| 可维护与可退出 | 系统更新、驱动冲突和卸载都有明确处理方式 | 不因后台失败留下占用磁盘的失效组件 |

### 2.3 “像系统自带”的具体定义

正常路径采用系统现有入口、位置、图标语义、进度和错误反馈。盘渡不建立第二套文件管理流程，不替换 Finder，不要求用户学习“先打开盘渡，再打开硬盘”。

这不意味着隐藏必要授权、伪装成 Apple 软件或省略重要失败提示。首次启用、写入受限、磁盘忙、格式化等需要用户理解的事件应明确呈现；品牌只保留在首次设置、设置窗口、关于和必要诊断位置。

### 2.4 不应作出的承诺

- 不以“支持 arm64”推导为“所有 M 系列与所有 macOS 均已实测”。
- 不承诺在任意损坏、断电、硬件故障下都绝不丢失数据。
- 不承诺永远免维护、永久兼容未来 macOS，或必然超过商业驱动的性能。
- 不把检测到驱动文件、系统报告可写或一次成功挂载，当作完整功能验收。

## 3. 用户、场景与成功路径

### 3.1 主要用户

首阶段首先服务当前用户本人，随后开展小范围试用；稳定后再决定公开发布。产品的主要用户是日常使用 M 系列 Mac、需要与 Windows 交换移动硬盘或 U 盘文件的人。其次是使用大文件、素材库、工程文件的创作者，以及仍需 Intel Mac 兼容的用户。默认不要求用户理解 FUSE、FSKit、挂载点或终端命令。

### 3.2 代表场景

| 场景 | 用户期望 | 系统行为 |
| --- | --- | --- |
| Windows 硬盘接入 Mac | 立即在 Finder 找到并继续工作 | 识别、检查、挂载，遵守已选择的读写策略 |
| 复制大文件或素材目录 | 使用 Finder 原有进度与取消方式 | 提供正确文件系统语义，不另建传输窗口 |
| 从应用直接保存到 NTFS | 与保存到其他外置盘相同 | 支持常见临时文件、重命名、同步与原子替换流程 |
| 编辑后拿回 Windows | 文件内容与名称保持可用 | 兑现成功同步与安全弹出的持久化语义 |
| 卷未安全移除或被 Windows 休眠占用 | 知道原因，有下一步操作 | 阻止不安全写入，必要时只读或拒绝挂载 |
| 平时不用外置盘 | 感受不到额外负担 | 不唤醒硬盘、不反复扫描、不显示主窗口 |

### 3.3 理想日常流程

首次完成安装与必要授权 → 插入硬盘 → 系统识别 → 快速检查卷状态和归属 → Finder 出现可用卷 → 用户正常读写 → Finder 安全弹出。

首次授权后，健康磁盘的重复使用不应要求再次输入密码、打开软件、点“启用写入”或处理弹窗。若操作系统规则必须交互，应在支持说明中如实说明，而不是绕过系统限制。

### 4.3 共同能力与本项目机会

调研支持将“文件系统级读写、自动挂载、系统文件操作、安全卸载、磁盘状态与异常说明”作为核心竞争能力 [S01–S06]。盘渡的机会是把这些能力组织成更安静、更少操作的体验，而不是增加一个更大的管理面板。

**应保留：** 稳定读写、插盘自动工作、常见文件操作完整性、可靠弹出、明确的只读原因、可维护的安装与卸载。

**应减轻：** 健康磁盘上的重复授权、强制主窗口、安装依赖拼装、正常事件通知、用户必须理解的底层术语。

**不作为卖点堆叠：** 资源监控仪表盘、无关清理功能、内置文件浏览器、排行榜式速度展示、强制账户与云服务。

## 5. 开源与基础组件分析

### 5.1 区分三个层次

NTFS 数据读写核心、接入 macOS 的文件系统机制、挂载与设置应用是不同层次。一个好看的挂载工具不代表具备自己的 NTFS 实现；核心能处理 NTFS 文件，也不代表已经满足 Finder、系统保存流程或休眠恢复的全部语义。

### 5.2 候选项目

| 项目 / 机制 | 已核实资料与角色 | 可用价值 | 必须核实的边界 |
| --- | --- | --- | --- |
| NTFS-3G / libntfs-3g | 上游提供跨平台 NTFS 读写核心及工具，列出 macOS；NTFS 组件为 GPL-2.0-or-later [S07] | 避免从零实现 NTFS；作为功能语义与测试参考 | 当前 macOS 适配、构建、错误传播、持久化，以及组合分发的许可义务 |
| Apple FSKit | 官方用户空间文件系统框架，以 app extension 交付，连接现有系统工具；文档可用性始于 macOS 15.4 [S08] | 最符合现代系统集成目标的优先研究入口 | 自动挂载竞争、授权、签名、版本差异和 IO 语义必须原型验证 |
| macFUSE | 提供 FUSE 接入及 FSKit 后端；文档规定该后端系统门槛并列出功能限制 [S09] | 快速复用 FUSE 生态，形成参考实现 | 不能默认等同内核后端能力与性能；适配层增加依赖；许可有额外限制 |
| Mounty | 主要承担用户入口和挂载编排 [S06] | 研究轻量交互与错误说明 | 不当作独立 NTFS 核心；不将其界面作为设计模板 |
| NTFSKit | 公开仓库包含基于 FSKit 和 NTFS-3G 的实现及 GPL 许可材料 [S10] | 检验直接适配 FSKit 的工作量，作为源码候选 | 尚未完成代码审计、维护持续性和异常恢复测试；作者性能声明不作为验收证据 |
| xNTFS | 公开项目介绍使用 FSKit 与 libntfs-3g [S11] | 观察系统集成方向和功能组织 | 必须核实可获得的完整源码、许可证与可复现构建；本轮不判定其可直接复用 |
| FUSE-T | 项目提供用户空间 FUSE 相关方案，公开资料涉及不同后端 [S12] | 作为替代适配路径调研 | NFS 与 FSKit 路径须分别看待；不能用某一后端的说明概括所有版本 |
| anylinuxfs | 使用轻量 Linux 虚拟机等组件访问 Linux 支持的文件系统 [S13] | 独立对照工具、兼容性研究 | 常驻资源、挂载语义及组件数量与“几乎无存在感”目标有张力，不列为默认路线 |

### 5.3 复用原则

先选择可以解释和验证的核心，再决定应用包装。评估代码质量、维护活动、回归测试、异常处理、构建可重复性、依赖和许可；不按下载量或 README 宣传排序。

任何引入都应记录上游仓库、固定提交、许可证、修改差异、构建方式与安全更新责任。不能因为项目“公开可看”就认定可自由复制；不能假定用独立进程包装就自动消除 GPL 义务。macFUSE 的商业集成或捆绑条件须按原始许可审阅 [S07、S09、S10]。

## 6. 产品范围与分期

### 6.1 优先级定义

- **P0：** 首个正式可用版本必须具备，否则不能称为完成 NTFS 读写产品。
- **P1：** 日常核心通过验收后补齐，扩大兼容与对标能力。
- **P2：** 成熟后的高级工具或独立扩展，不能拖累 P0。

“首版”指首个正式可用版本，不是只显示磁盘列表的检测预览。原型可以功能不完整，但必须明确标识。

### 6.2 分期边界

| 阶段 | 交付范围 | 不应混淆的界限 |
| --- | --- | --- |
| 决策整合 | 三轮关键选择、需求 v0.2、实施计划与待验证清单 | 当前已交付文档；尚未同意开始编码 |
| 技术验证 | 测试镜像上证明系统接入、读写语义、授权与基本性能 | 不面向重要数据，不宣称日常可用 |
| M 系列正式首版 | P0 功能、Finder 工作流、可靠读写、安装卸载和完整质量门槛 | 无读写能力的界面不满足首版定义 |
| 兼容与完善版 | Intel x86_64、更多系统组合、进阶元数据与系统功能 | 原有 Intel 目标继续保留，发布时间单独确认 |
| 高级工具版 | 检查、NTFS 格式化、受限修复及更多可选功能 | 破坏性操作单独入口、授权和验收 |

### 6.3 明确不在首版范围

从零编写完整 NTFS 驱动、BitLocker 解密、EFS 解密、文件恢复、分区调整、启动盘与 Boot Camp 管理、RAID 管理、远程挂载、跨平台同步、云备份以及全能磁盘清理工具不属于 P0。

NTFS 压缩、稀疏文件、ADS、重解析点等复杂特性需形成逐项能力表。未承诺的操作必须明确拒绝或按可靠策略只读处理，不能悄悄破坏原有内容或元数据。

## 7. 功能需求

### 7.1 磁盘识别与系统接入

| 编号 / 级别 | 需求 | 关键验收条件 |
| --- | --- | --- |
| F-01 / P0 | 自动发现外置设备和其中的 NTFS 卷 | 热插拔、多分区、多卷与多设备可识别；依据实际文件系统，不依据名称或通用 Windows 分区类型猜测 |
| F-02 / P0 | 健康且受支持的卷按用户策略自动读写挂载 | 首次设置统一开启后，健康、受支持、无冲突的外置 NTFS 无需逐盘确认；单卷只读策略优先；Finder 不出现重复入口 |
| F-03 / P0 | 支持只读、自动读写和暂不接管策略 | 全局和单卷策略清楚，能解释最终生效的访问状态；不以只读挂载充当可写成功 |
| F-04 / P0 | 仅接管明确属于本产品范围的卷 | 默认只处理外置 NTFS，不干预 APFS/exFAT/FAT 与系统卷；内部卷暂不自动接管 |
| F-05 / P0 | 防止错误设备与重复挂载 | 每次改变状态前重新确认设备身份和当前归属；名称相同、设备号复用、UUID 重复时不得套错策略 |
| F-06 / P0 | 处理系统与第三方驱动竞争 | 不抢占忙卷、不静默卸载其他驱动管理的卷；冲突时说明归属并提供恢复路径 |

| F-09 / P0 | 支持常见应用保存语义 | 临时文件、同卷原子重命名、替换保存、截断、随机写、并发读取和必要锁语义通过测试 |
| F-10 / P0 | 正确兑现同步与错误反馈 | flush/fsync/close 的约定明确；磁盘写满、权限拒绝、IO 失败不得报告成功；已确认持久化的数据需经过重新挂载验证 |

## 8. 原生体验与 UI 需求

### 8.1 日常“无主界面”

盘渡的主要工作空间是 Finder。没有强制仪表盘，没有独立文件浏览器，没有每次插盘的欢迎窗口，没有为正常操作增加的品牌浮层。

UI 只承担首次设置、偏好设置、单卷状态、必要异常和关于/诊断。使用系统字体、原生控件、标准间距、系统图标语义、标准键盘行为和系统浅深色；依据 Apple HIG 与真实系统工作流设计 [S15]。

### 8.2 已确认的默认入口

| 入口 | 默认行为 | 内容 |
| --- | --- | --- |
| Finder / 标准文件对话框 | 日常唯一必要入口 | 浏览、保存、复制、移动、删除、弹出 |
| 盘渡设置窗口 | 用户主动打开时出现 | 自动读写、单卷策略、状态、更新、诊断 |
| 菜单栏入口 | 默认常驻一个小图标，可在设置中隐藏 | 精简卷状态、设置；可选轻微读写动态，不展示无关指标 |
| Dock | 不常驻 | 仅在用户主动打开前台窗口时遵循系统行为 |
| 系统设置中的扩展/后台项管理 | 尊重系统提供的页面 | 提供准确引导，不承诺在系统设置中插入任意自定义页面 |
| 系统通知 | 仅必要异常 | 一句话原因及最少可行动入口 |

无需申请 Finder 装饰性角标或添加自定义右键菜单才能使用基本功能；只有标准系统行为确实不能完成必要操作时，才评估扩展入口。

### 8.3 建议的信息结构

设置窗口采用紧凑的系统设置式组织，但不复制任何第三方产品布局：

- **通用：** 自动读写、菜单栏图标显示、读写动态效果开关、更新策略。
- **磁盘：** 当前卷、实际访问状态、单卷读写策略与原因。
- **诊断：** 组件状态、错误摘要、导出报告。
- **关于：** 版本、发布者、许可、支持方式和卸载入口。

无需在首版预设复杂侧栏、首页卡片或固定尺寸。具体控件与布局在需求确认后做低保真设计，由真实信息量决定。

### 8.4 示例文案

| 情境 | 推荐表达 |
| --- | --- |
| 正常读写 | 不弹窗；用户查看状态时显示“可读写” |
| 健康但选择只读 | “只读：已按此磁盘的设置关闭写入。” |
| Windows 休眠状态 | “此磁盘可能仍被 Windows 休眠会话占用。已暂停写入，请回到 Windows 完整关机后重试。” |
| 弹出时被占用 | “磁盘正在使用中。请关闭相关文件后再次弹出。” |
| 不支持的加密卷 | “此磁盘已加密，盘渡暂不能直接读写。请先使用支持该加密方式的系统或工具解锁。” |
| 引擎不可用 | “NTFS 写入暂不可用。现有读取是否可继续，取决于系统当前挂载状态；可打开诊断查看原因。” |

示例必须与实际检测证据相匹配；不能在未确认休眠时断言“Windows 正在休眠”。

### 8.5 原生菜单栏动态效果：可行性与范围

**资料已核实：** AppKit 的 `NSStatusItem.button` 允许通过公开接口设置状态栏按钮的图像；SwiftUI 的 `MenuBarExtra` 提供持久菜单栏入口，并有不常驻 Dock 的系统配置方式 [S16、S17]。因此，使用公开接口按状态切换图像，制作轻微活动效果在工程上可行。本文尚未运行原型，不宣称某一种动画 API 已在菜单栏和 macOS 26.5 上通过验证。

**实现倾向：** 优先评估 AppKit `NSStatusItem` / `button.image` 控制图标，设置内容可使用原生 SwiftUI/AppKit。若采用 SwiftUI 菜单栏路径，须单独验证动态图像刷新及生命周期，不预设 `symbolEffect` 在标签中一定持续工作。不使用私有接口、屏幕读取、对 Finder 的代码注入或额外用户驱动来实现图标。

**活动的含义：** 表示“观测到盘渡管理的 NTFS 卷存在读写活动”，不等于 Finder 正在拷贝某个文件。预览、应用保存与后台访问也可能产生 IO；本期不读取 Finder 任务、不采集文件名或任务总字节数。缓存与不同 IO 路径可能影响可观测事件；若采用 FSKit 的内核卸载 IO 能力，需重新验证活动信号覆盖，不能只靠普通读写回调数量判断 [S19]。

| 情境 | 期望呈现 | 约束 |
| --- | --- | --- |
| 空闲 / 无管理卷 | 单色静态图标 | 无装饰循环动画，无为图标而进行的磁盘扫描 |
| 可观测读写活动 | 轻微图像变化或短周期活动效果 | 保持图标宽度；不跳动菜单栏位置，不显示进度百分比，不逐 IO 驱动 UI |
| 活动停止 | 经短暂平滑处理返回静态 | 停止动画不表示缓存已持久化，也不意味着磁盘可以拔出 |
| 多个管理卷同时活动 | 聚合一个活动状态 | 不读取卷内文件清单，不在图标上循环播报文件名 |
| 减少动态效果 / 用户关闭效果 | 静态图标，必要状态在菜单中查看 | 响应系统无障碍设置；不以动画作为唯一状态信号 [S18] |
| 数据源不可用 / 扩展断开 | 静态或明确的未知状态 | 不用定时器制造假活动，不影响文件 IO |
| 需要处理的错误 | 稳定的状态标记与菜单内说明 | 不用持续闪烁代替错误解释 |

**建议约束：** 动态效果刷新初始上限为每秒 2 次，采用事件聚合；动画关闭、活动结束、图标隐藏、锁屏或睡眠时停止无必要的动画定时工作。该频率是待原型校准的预算，不是用户已经选定的视觉方案。保持模板图像的系统适配方式，并验证深浅色、显示缩放、菜单展开、VoiceOver 和“减少动态效果” [S18、S20]。

**降级规则：** 若公开接口效果不稳定、活动状态不可信或资源开销不合适，首版交付静态菜单栏图标。F-36 的缺失不降低文件读写、异常解释或安全弹出的 P0 标准。

## 9. 自动化策略与状态边界

### 9.1 已确认的默认策略

首次设置由用户统一明确开启“自动读写健康的外置 NTFS 磁盘”。此后健康、受支持、无冲突的外置卷无需逐盘确认即按策略工作；用户可对特定卷保持只读或暂不接管。

只读策略优先于自动读写；安全检查不通过优先于任何读写偏好；第三方驱动拥有挂载或卷正忙时，不直接覆盖其状态。

### 9.2 关键状态转换

| 当前状态 / 事件 | 下一状态 | 规则 |
| --- | --- | --- |
| 新卷出现 | 识别中 → 检查中 | 重新确认实际设备与文件系统，不复用旧设备号授权 |
| 健康、支持、无冲突、允许写入 | 可读写 | 完成系统挂载并验证状态后才宣告可用 |
| 用户只读策略 | 只读 | 说明原因，不显示错误级警告 |
| dirty / 休眠 / 加密 / 未知 | 只读或不可用 | 根据可靠能力选择，不能为了显示可用而强制写入 |
| 已被其他驱动管理 | 冲突/由其他驱动管理 | 可显示系统实际能力，但不冒认为盘渡提供 |
| 正在 IO 时请求切换或弹出 | 忙 / 等待用户处理 | 不强制中断；取消请求不改变原策略 |
| 意外移除 | 已移除 | 停止后续操作，废弃旧句柄与状态；重复接入重新检查 |
| 扩展崩溃或系统升级后不兼容 | 降级或不可用 | 有限重试，给出原因；不循环重挂载 |

**只读降级有前提：** 必须能够可靠完成只读访问并妥善处理当前卷状态。无法安全降级时应停止操作并解释，不保证所有故障都能无缝恢复只读。

### 9.3 已确认的更新策略

默认自动检查版本更新，安装必须由用户确认；检查失败、断网或用户暂不更新均不阻断正常离线读写。检查请求仅包含判断适用版本所必需的最少产品/系统信息，不包含卷名、磁盘标识、挂载路径、文件名、磁盘内容或磁盘使用情况。具体字段、检查频率与下载时机在设计阶段写明，不默认收集遥测。

用户确认安装后，仍须等待盘渡管理的可写卷全部安全弹出；“当前没有观测到 IO”或“图标已静止”不是更新引擎的充分条件。安装前重新检查状态、阻止新增接管与安装之间的竞态，且不主动强制卸载硬盘。其他第三方组件的全局卷限制也必须遵守。

正式更新入口尚未确定。在仅自用的早期阶段，可以尚无可用更新源，但应如实呈现，不以模拟版本检查冒充功能。进入可用交付阶段时再验证签名清单、更新包、兼容规则、失败回退和离线行为。

## 10. 兼容性要求

### 10.1 芯片优先级

| 类别 | 目标 | 交付口径 |
| --- | --- | --- |
| Apple Silicon M 系列 | 第一优先级，arm64 原生 | 覆盖各代及 Pro/Max/Ultra 产品线的架构目标；公开实际测试过的机器与系统组合 |
| Intel Mac | 后续 x86_64 目标 | 不包含历史 32 位 x86；若无法使用同一后端，必须评估差异并另行确认 |
| Rosetta | 不作为 M 系列默认路径 | 不以 Rosetta 能运行界面代替原生驱动兼容 |

既要覆盖最早一代 M 系列的代表设备，也要覆盖一台较新的 M 系列，以及至少一类 Pro/Max/Ultra 设备。USB 控制器、桥接芯片、外设与 macOS 版本同样属于兼容性维度；不能只按 CPU 名称打勾。

### 10.2 已确认的系统验证起点

用户已确认先以当前 macOS 26.5 为第一验证基线。FSKit 官方文档标注从 macOS 15.4 可用，macFUSE 的 FSKit 后端也有相应系统门槛 [S08、S09]；这只是 API/后端可用的起点，不是盘渡的兼容性结论。

**已确认顺序：** 先验证当前环境；取得原型证据后，再选择扩展的系统组合并冻结最低支持版本。本版没有承诺从 15.4 起全部兼容，也没有把较旧系统加入首阶段硬性范围。任何扩展都必须满足保持默认安全设置的已确认约束。

### 10.3 存储介质与布局

P0 覆盖健康的常见 Windows NTFS 3.x 外置卷，包含 USB U 盘、移动 HDD、移动 SSD、USB-C/雷雳外置盒及常见扩展坞路径。分别验证 GPT、MBR、单卷、多分区、相同卷名、多设备同时插入、大于 2 TB 介质以及实际可获得的 512e/4Kn 组合。

不把外置盒正常报告容量等同于卷结构可靠。加密、RAID、动态磁盘、特殊 Windows 数据结构及未知特性列明支持状态；没有证据时不自动启用写入。

## 11. 技术路线分析与选型门槛

### 11.1 候选路线

| 路线 | 与产品目标的关系 | 优势 | 风险与处理 |
| --- | --- | --- | --- |
| A. NTFS 核心直接适配 FSKit | 推荐主路线，待验证 | 系统用户空间入口，组件关系相对直接，可围绕原生体验设计 | 适配成本、文件系统语义、授权/挂载机制及性能需实证；评估 NTFSKit 等源码时先审查 |
| B. NTFS-3G + macFUSE FSKit 后端 | 对照原型与备选 | 更快复用 FUSE 路径，能与上游行为比较 | 接口限制、额外组件和许可约束；不是未经验证就锁定的最终架构 |
| C. 其他用户空间桥接 | 备选研究 | 可能减少内核依赖或补充兼容 | 必须检查额外网络/虚拟机语义、资源开销和分发条件 |
| D. 要求降低启动安全的内核扩展路线 | 已排除 | 不进入本项目的动手验证或交付 | 用户要求全部验证和日常使用均保持默认安全设置 |
| E. 从零实现 NTFS | 不建议启动 | 自主程度最高 | 数据一致性、格式覆盖、维护与测试成本过高 |

FSKit 是系统接入框架，不直接提供完整 NTFS 读写实现。用户空间扩展隔离也不等于免除数据一致性问题 [S08]。

### 11.2 推荐路线与模块边界

**推荐先验证：原生 FSKit 文件系统扩展 + 可复用 NTFS 核心，首先评估 libntfs-3g。** NTFSKit 等已有实现可作为审查参考，但未经审计不直接作为发布依赖。macFUSE 的 FSKit 后端保留为对照或备选，前提是同样满足安全、安装、性能和许可约束。当前不承诺直接适配一定优于中间适配层。



Finder / 常用应用 → macOS 文件系统接口 → 选定的文件系统扩展或适配层 → NTFS 核心 → 受控块设备资源。

设置、诊断、挂载策略与状态管理放在独立控制层；文件数据路径不依赖设置窗口或菜单栏展示进程存活。菜单栏按已确认选择默认常驻，但移除图标、关闭设置或重启展示进程不应破坏卷的数据通道。SwiftUI 仅菜单栏应用被用户移除入口时可能自动终止，生命周期必须专门验证 [S17]。是否需要额外特权服务，由 FSKit 资源访问与挂载原型决定，不预先引入常驻 root helper。

活动汇总应优先来自引擎或挂载控制层的低成本可信事件，不记录文件内容和名称，不将图标动画放入关键 IO 路径。

### 11.3 必须先回答的技术问题

1. 能否在目标 M 系列环境维持默认启动安全策略完成安装、启用和读写？
2. 能否自然地完成自动接管，避免系统只读挂载与第三方驱动之间的竞态？
3. 是否支持 Finder 与常见应用需要的保存、锁、同步、缓存、随机访问和错误语义？
4. 断开、休眠、崩溃、磁盘写满之后，数据与状态是否可解释、可恢复？
5. 正常插盘与空闲资源占用是否达到本产品的低存在感要求？
6. 性能是否足以支持大文件和大量小文件，瓶颈能否归因并改善？
7. 许可、签名、公证、扩展授权及依赖分发能否形成可持续的正式交付方式？
8. 菜单栏活动是否能在普通及候选卸载 IO 路径下可靠汇总，并满足原生外观、低开销和静态回退要求？
9. 更新检查、用户确认、卷弹出、停止新接管及组件更换之间，是否形成无竞态且可回退的流程？

以上问题没有通过验证前，不冻结唯一后端，不依据界面完成度宣称产品可用。

## 14. 许可、分发与成本边界

### 14.1 已接受开源义务，具体许可仍待核实

NTFS-3G 的 NTFS 组件使用 GPL-2.0-or-later；相关项目和捆绑方式可能带来源码交付与许可兼容要求。macFUSE 使用其自身许可，并对商业集成或捆绑设有条件 [S07、S09]。最终分发结构需按实际代码和许可审查，不能仅按“免费”或“独立进程”判断。

用户已接受复用组件所要求的开源义务：当前先私有自用；未来分发时愿意按实际许可证提供相应源码。进入集成前仍需形成固定版本的组件清单、修改记录、相应源码交付范围及许可兼容说明；接受义务不等于已经选定整个项目的许可证，也不意味着现在公开仓库或允许任意渠道分发。小范围试用涉及向他人提供软件时，同样要先核实所需义务。FSKit 的扩展分发能力不自动解决组合许可问题 [S07、S08、S09]。

### 14.2 用户成本目标

不以重新购买既有 Paragon 授权作为项目解决方案，不把常规离线读写绑定云端服务。开发者签名、公证相关账户、组件商业许可、测试硬件及长期维护可能产生独立成本；本文不提供未经核实的零成本或终身免费保证。

### 14.3 分发建议

优先研究可验证的直接分发方式，降低完整 NTFS 能力与组件许可的渠道不确定性。Mac App Store 可作为后续选择，需要按最终扩展、权限、许可及审核条件单独评估，不设为首版强约束。

## 15. 风险与取舍

| 风险 | 影响 | 处理与决策条件 |
| --- | --- | --- |
| FSKit 适配存在语义或性能缺口 | 无法满足原生体验或质量门槛 | 以原型与对照测试作选择；不因概念先进就强行采用 |

| M 系列覆盖被宣传过度 | 用户误用未验证组合 | 明确架构目标与实测矩阵，不泛化为全设备保障 |
| 格式化/修复过早加入 | 扩大高影响失败范围 | P2 单独开发、授权、测试和发布 |
| 过度追求“无感” | 用户无法理解故障或停用软件 | 正常路径安静，异常解释清楚，设置入口始终可找到 |
| 旧系统兼容拖累主要体验 | 增加依赖与安装步骤 | M 系列现代系统优先；Intel/旧系统独立验收与取舍 |

### 16.1 实施顺序建议

1. **组件与许可核实：** 固定 NTFS 核心及参考实现版本，核对可复现构建、许可和签名/扩展交付条件。

3. **文件语义与一致性：** 建立大文件、随机写、原子保存、同步、写满、崩溃及 Windows 往返证据；无法证明时先解决核心问题。
4. **菜单栏与控制层：** 验证常驻图标、无 Dock 常驻、设置入口、活动汇总和静态回退；不让界面先行替代核心验收。
5. **日常闭环：** 完成单卷策略、忙卷弹出、休眠恢复、错误说明与诊断。
6. **统一交付与更新：** 完成签名、公证、首次授权、版本检查、用户确认、安全更新和卸载；在无 Homebrew 的干净环境验证。
7. **扩大覆盖：** 先本人日用，再小范围试用；依据证据增加 M 系列/系统组合，Intel 为后续兼容阶段。

详细任务、可交付证据和停下条件见同目录《DiskFerry-技术路线与实施计划-v0.2.md》。开发时间与预算在 G1 后给出更可信估算，本文没有安排实际开始日期，也不以 UI 页数推算文件系统工作量。
