## 1. 已确定的方向

- 先满足本人日用，再小范围试用；稳定后再决定是否公开发布。
- M 系列优先，以当前 macOS 26.5 为技术验证起点；后续基于证据扩大系统与机型范围，保留 Intel 兼容目标。
- 首个日常可用版本完成 Finder 读写、自动挂载、安全弹出和异常处理；格式化、修复等后置。
- 接受复用组件要求的开源义务，目前私有自用；未来分发前核实并履行相应源码交付与其他许可要求。
- 首个日常可用版本统一安装，不要求用户使用 Homebrew 或拼装依赖。
- 全部验证和日常使用均保持系统默认安全设置，排除降低启动安全策略、关闭 SIP 的路线。
- 默认常驻菜单栏小图标，不主动打开主窗口，Dock 不常驻；图标动态为有条件增强。
- 首次设置统一开启后，健康、受支持、无冲突的外置 NTFS 自动读写；允许单卷只读例外。
- 自动检查更新、不上传磁盘信息；用户确认后，等待受管理的可写卷全部安全弹出再更换组件。

## 2. 推荐技术路线

### 2.1 主路线：原生 FSKit + 现有 NTFS 核心

优先验证 Apple FSKit 文件系统扩展与 libntfs-3g 的适配。FSKit 提供系统接入与受控资源访问入口，NTFS 核心处理格式和文件语义；挂载策略、设置、诊断与菜单栏属于控制层。此选择是工程倾向，不是已证实的最终架构 [R1、R2]。

首先审查核心的块设备 IO 抽象：若原有实现依赖普通文件描述符或直接设备访问，必须证明它能通过 FSKit 授予的资源正确完成读、写、同步、错误返回与生命周期管理。不能把一个用户态库编译成功当作已完成系统适配。

NTFSKit 等现有实现可用于了解适配工作与风险，但引入前应核实完整源码、固定提交、许可证、修改范围及回归质量。不得只依据作者的速度或兼容宣传决定采用。

### 2.2 备选：macFUSE 的 FSKit 后端

用于必要的对照与备选，仍须满足统一安装、默认安全设置及组件分发许可。它的 API 覆盖和性能必须独立测试，不能照搬其他后端的能力说明。若主路线受阻，先说明具体障碍和备选影响，再调整方案；不自动退回需要降低安全策略的路线 [R3]。

### 2.3 控制层与菜单栏

菜单栏优先评估 AppKit `NSStatusItem` 的公开图像更新能力；设置与轻量状态界面采用原生 SwiftUI/AppKit。SwiftUI `MenuBarExtra` 也是原生入口候选，但图标刷新和“仅菜单栏应用被移除后自动退出”等生命周期行为须单独核实 [R4、R5]。

文件数据通道不得依赖菜单栏图标或设置窗口存活。展示进程退出、图标隐藏或诊断不可用时，不能自行终止已挂载卷的 IO。控制层与数据层之间的通信方案、授权与失效行为均属于原型验证范围。

活动信息优先来自引擎或挂载控制层的可信事件，并按卷聚合。不监控 Finder 屏幕、不读取文件清单、不使用私有接口或注入，不将 UI 更新放进关键 IO 路径。存在缓存或卸载 IO 路径时，要证明信号的含义和覆盖范围；不能单靠回调频率伪装完整复制进度 [R8]。

### 2.4 架构职责

| 模块 | 职责 | 必须守住的边界 |
| --- | --- | --- |
| 文件系统扩展 / 适配层 | 对接 macOS 文件系统操作与资源访问 | 正确的 IO、同步、错误、取消及资源生命周期 |
| NTFS 核心 | 格式解析、文件/目录与元数据操作 | 不信任磁盘输入；保留支持边界；禁止静默损坏 |
| 挂载策略控制 | 识别、健康检查、归属与读写策略 | 设备身份重验；不强制抢占忙卷，不误用旧设备号 |
| 菜单栏与设置 | 精简状态、偏好、诊断、更新入口 | 默认常驻图标，无主动主窗口，无常驻 Dock |
| 活动汇总 | 聚合受管理卷的可观测活动 | 不采集内容或路径，不伪造百分比，不决定安全弹出 |
| 更新与交付 | 包校验、用户确认、闲置条件、回退 | 没有 IO 不等于可更新；可写卷须全部安全弹出 |

## 3. 分阶段实施顺序

### G0：需求与决策整合——当前已完成的文档阶段

成果为需求说明书 v0.2、三轮决策记录和本计划。此前试验代码和界面不作为已批准的实现基础，不复用其完成状态来抵扣新需求。

下一阶段只有在用户另行明确要求开始后才启动；本次不询问或代替用户作出开发授权。

### G1：技术验证——计划，尚未执行

**G1-A 组件、许可与交付条件。** 固定核心候选与参考实现提交，确认可获得的源码、构建方式、许可证和分发义务；核实开发者签名、FSKit 授权和统一安装路径。若需要额外特权服务，说明必要性、权限范围和替代方式。

**G1-B 原生系统接入。** 在 macOS 26.5、默认安全设置下，用一次性镜像验证资源识别、只读接入、扩展启用、挂载归属和卸载。之后验证受控写入及系统内建 NTFS 只读挂载之间的协调。需要签名账户或额外测试环境时，应如实列为前提，不改系统安全策略来绕过。

**G1-C 最小读写语义。** 在镜像中证明新建、覆盖、重命名、截断、随机写、大文件、Unicode 名称、同步和错误传播；对 Windows 创建及检查过的固定样本进行回读。对脏卷、休眠、加密和未知状态明确拒绝写入策略。

**G1-D 安装和性能的早期证据。** 提前确认不要求用户拼装依赖的交付方式；比较原始核心/参考路径与适配层的性能，记录环境和版本，不先许诺竞品速度。

**G1-E 菜单栏独立验证。** 验证公开接口图像更新、模板图像、深浅色、菜单展开、系统减少动态效果和实际活动信号。活动信号尚未接入时只能明确使用模拟状态来验证 UI，不能当作真实磁盘活动展示；真实 IO 可靠性必须另测。

G1 的交付物应包含：可复现说明、组件与许可清单、镜像和数据样本来源、验证记录、核心失败清单、性能基线与后端选择建议。主路线不满足硬约束时停止推进该路线；不靠扩大权限、隐藏错误或降低测试标准通过。

### G2：首版功能闭环——计划，依赖 G1

依据选定后端完成以下顺序：

1. 设备身份、挂载归属与只读/自动读写策略。
2. 健康外置卷自动读写，以及失败时可靠的只读或不可用状态。
3. Finder 与常见应用的完整文件操作、保存与异常反馈。
4. 忙卷处理、安全弹出、意外断开和休眠恢复。
5. 菜单栏常驻、原生设置、明确错误说明、受控诊断导出。
6. 活动动态的条件实现；不满足要求时静态交付。
7. 统一安装、更新检查/确认/安全更换、失败恢复与卸载。

完成条件是 P0 能够串成真实日常使用闭环；仅有磁盘列表或可点击界面不算完成。

### G3：可靠性与互操作——计划，依赖 G2

使用一次性镜像和明确指定的可清空测试介质，执行正常与异常用例。覆盖大文件、小文件、深目录、多卷并发、写满、错误、取消、崩溃、正常弹出、意外拔盘、重启和休眠；对 Mac / Windows 双向内容、名称、元数据和卷一致性分别验证。

哈希一致只证明文件内容，不能替代 ACL、ADS、时间戳和卷结构检查。测试记录需区分已成功持久化与未完成写入，不承诺硬件断电下任意未提交数据都完整保留。

正式可用前达到需求书中的发布门槛；建议数值在 G1 后冻结。对当前无法覆盖的机型、系统或特性明确列为未验证。

### G4：本人日用与小范围试用——计划，依赖 G3

统一交付签名、公证、首次设置、必要授权、许可告知、诊断、更新与卸载。在不预装 Homebrew 或其他候选依赖的干净环境验证完整流程。

先本人日用，发现问题回到对应技术阶段；稳定后再小范围试用。向其他人提供软件前核实并落实许可义务，不能把“仅小范围”当作免除分发要求。此阶段不默认公开仓库、不上架商店、不安排收费。

更新源、发布者身份、版本匹配、签名清单和回退方案须落实；未具备真实更新源时如实标明，不能模拟“检查成功”。

### G5：扩大兼容与高级功能——后续计划

依据 G1–G4 证据冻结最低系统版本，增加代表性 M 系列和外设组合；Intel x86_64 单独完成真机验收。高级只读检查、复杂 NTFS 元数据、格式化和有限修复分别立项，保持原有优先级，不倒逼首版修改已确认安全原则。

| 编号 | 问题 | 需要的证据 | 性质 |

## 5. 菜单栏动态效果的专项范围

原生状态栏允许通过公开接口更换按钮图像，因此轻微活动效果有可行路径 [R4]。本期的视觉方向是：静态单色小图标、活动期间克制变化、结束后恢复；具体样式在后续原型中选择，不参考竞品 UI。

- 仅显示受盘渡管理卷的可观测读写活动，可将多卷汇总为一个状态。
- 不推测文件总量、拷贝百分比、剩余时间，不读取文件名；真实文件进度仍使用 Finder。
- 动画结束不代表缓存完成落盘，也不代表可以拔盘；安全弹出是独立流程。
- 初始刷新预算为每秒最多 2 次，按事件聚合，避免每次 IO 唤醒 UI；该预算尚未实测或冻结。
- 保持图标尺寸和菜单栏位置，采用原生模板图像，验证深浅色、显示缩放和菜单交互 [R7]。
- 系统启用减少动态效果或用户关闭动画时，用静态呈现；图标隐藏、锁屏、睡眠或空闲时停止无必要动画工作 [R6]。
- 信息源失效、候选卸载 IO 路径无法可靠观察、动画不稳定或资源消耗过高时，回退静态，不模拟磁盘忙碌。

## 6. 更新的专项约束

自动检查只获取判定版本适用性所必需的最少信息。请求字段与日志明确列出，不上传磁盘名称、标识、路径、文件信息、内容或使用状态；不将检查更新变成激活或正常读写的必要条件。

安装流程必须满足：用户确认 → 盘渡管理的可写卷全部成功安全弹出 → 再次确认资源/句柄状态并阻止新增接管竞态 → 校验可信更新包 → 更换组件 → 确认可运行并恢复正常策略。

若采用的第三方组件有更严格的全局卸载前提，还须遵守这些要求。任一环节失败时保持或恢复可诊断的状态；不得以“菜单栏图标静止”或“最近没有 IO 事件”替代卷已安全卸载的判断。
